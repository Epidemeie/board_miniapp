# Tbilisi Services — Frontend (Telegram Mini App)

React + Vite фронтенд локального маркетплейса услуг для Тбилиси.
Работает как Telegram Mini App — открывается изнутри Telegram-бота.

## Стек

- React 18, обычные хуки (без роутера, без стейт-менеджера — навигация
  между экранами реализована вручную через `useState` + `history`-стек
  в `src/App.jsx`)
- Vite для сборки
- Один файл — `src/App.jsx` — содержит всю логику и все экраны
  (осознанно не разбито на компоненты по файлам, проект маленький)
- Стили — инлайн `<style>` внутри `App.jsx`, без Tailwind/CSS-фреймворков
- Деплой: Vite build → статика → Docker/Nixpacks через Coolify

## Backend

Всё общение с сервером — через `API_BASE` в начале `App.jsx`:
```js
const API_BASE = "https://api.goservices.lol/api";
```
Backend — отдельный репозиторий `board_miniapp_backend`, модульный
Express + Prisma + PostgreSQL. Список эндпоинтов и их поведение — см.
`CLAUDE.md` и `README.md` в том репозитории. Перед изменением того,
что и как фронтенд отправляет на сервер (структура тела запроса),
сверяться с бэкендом — контракт может сломаться в обе стороны.

## Роли: клиент / мастер

Экран `role` — выбор роли, ключевая механика приложения:
- **Клиент** — создаёт заявку, видит подобранных мастеров (алгоритм
  на backend), позже смотрит отклики в «Мои заявки» и выбирает мастера.
- **Мастер** — при первом входе проходит короткую саморегистрацию
  (`POST /providers/register`), дальше видит открытые заявки под свою
  услугу и откликается ценой + комментарием.

Роль выбирается один раз и дальше персистится на backend как
предпочтение входа — `User.entryRole` (`client`/`provider`/`null`),
через тот же `PUT /api/users/prefs`, что и язык. Это отдельное поле от
`User.role`, которым управляет сам backend по факту регистрации
(`providersService` выставляет `role: "provider"` при регистрации и
возвращает `role: "client"` при удалении профиля мастера) — `entryRole`
только про то, в какой кабинет открывать приложение, и не трогается
этой логикой.

При каждом запуске `useEffect` в начале `TbilisiMiniApp` запрашивает
`GET /api/users/prefs/:telegramId`; если `entryRole` уже выбран — сразу
вызывает `chooseClient()`/`chooseProvider()` (минуя экран `role`),
которые сами решают, куда вести дальше (например, `chooseProvider()`
уводит на `provider-register`, если `Provider`-профиля ещё нет). Если
`entryRole` пуст — показывается экран `role`, а нажатие на карточку
идёт через `pickClient()`/`pickProvider()`, которые запоминают выбор
через `persistPrefs({ entryRole })` и затем делают то же самое, что
`chooseClient()`/`chooseProvider()`.

Сменить роль позже можно из настроек — блок «Режим» на экранах
`client-profile` (кнопка «Перейти в кабинет мастера») и
`provider-settings` (кнопка «Перейти в кабинет клиента»), оба вызывают
`pickProvider()`/`pickClient()` напрямую. Регистрация мастера при этом
не удаляется — переключение туда-обратно не теряет `Provider`-профиль.

## Рейтинг клиента (симметрично рейтингу мастера)

У клиента, как и у мастера, есть рейтинг и отзывы — только в обратную
сторону: их оставляют мастера после завершения заказа. Всё зеркально
существующему коду про рейтинг мастера, ищи по аналогии `provider*` ↔
`client*`:
- `clientProfile` (state) — публичный профиль клиента с рейтингом,
  загружается в `chooseClient()` через `loadClientProfile()`
  (`GET /users/by-telegram/:id` → `GET /users/:id`), аналогично тому,
  как `chooseProvider()` грузит `provider`.
- `getClientReviewStats()`/`getClientReviewDistribution()` — зеркало
  `getReviewStats()`/`getReviewDistribution()`.
- Экраны `client-reviews`/`client-reviews-all` (`renderClientReviews`)
  — зеркало `provider-reviews`/`provider-reviews-all`. Вход — карточка
  «⭐ Мой рейтинг» на `client-dashboard` и ссылка в `client-profile`.
- На стороне мастера рейтинг клиента виден в ленте новых заявок
  (`renderProviderRequests`, таб «Новые») и в деталях заказа
  (`renderProviderOrderDetail`, блок «Клиент»).
- Отзыв о клиенте мастер оставляет на экране `provider-client-review`
  (`renderProviderClientReview`, `submitClientReview` → `POST
  /client-reviews`) — кнопка появляется в `renderProviderOrderDetail`,
  только когда `request.status === "completed"` (заказ уже завершён
  клиентом) и у мастера ещё нет отзыва по этой заявке
  (`o.request.clientReviews.length === 0`, приходит из
  `GET /offers/mine`). Источник истины — только backend, никаких
  локальных «уже оставил отзыв» флагов в состоянии (см. похожий баг,
  который чинили с `locallyCompletedRequestIds` — не повторять).

## Идентификация пользователя

`getTelegramUser()` в начале файла читает
`window.Telegram.WebApp.initDataUnsafe.user` — это реальные Telegram ID,
имя, username человека, открывшего Mini App. Никакой отдельной формы
логина/регистрации для клиентов нет и не должно быть — Telegram уже
идентифицирует человека.

Вне Telegram (обычный браузер, для разработки) используется
фоллбэк — случайный `demo-...` ID в `sessionStorage`, чтобы можно было
тестировать локально без реального Telegram-контекста.

## Известные особенности (не баги)

- Экран матчинга (`client-matches`) — информационный: после создания
  заявки клиент видит список подходящих мастеров и их разбивку по
  алгоритму, но это не «отправка заявки конкретным N мастерам» — заявка
  просто становится видна всем мастерам с такой услугой через их ленту
  открытых заявок. Пуш-уведомлений мастерам пока нет (не реализовано
  на backend) — они должны сами периодически открывать Mini App.
- AI-автоопределение категории по свободному тексту (было в раннем
  прототипе) — сейчас убрано ради простоты, категории выбираются
  вручную через список. Если возвращать — см. историю коммитов, была
  рабочая версия через прямой вызов `api.anthropic.com/v1/messages`
  из браузера.

## Локализация (ru/en)

Экран `language` показывается только при первом открытии приложения.
Выбор персистится на backend в `User.language` по `telegramId`
(`GET/PUT /api/users/language`, публичный роутер в
`mini-app-backend/src/modules/users/router.ts`) — работает и для
клиента, и для мастера, это один и тот же `User`. `localStorage`
(`app_language`) — быстрый локальный кэш для мгновенной отрисовки и
фолбэк, если backend недоступен при загрузке. При каждом запуске
компонент (см. `useEffect` в начале `TbilisiMiniApp`) сперва временно
показывает пустой экран `boot`, запрашивает сохранённый язык и уже
тогда решает, показать `language` (язык ещё не выбирали) или сразу
`role`. Сменить язык позже можно ненавязчивым переключателем
RU/EN (`.tms-lang-pill`) на экране `role`, без возврата на `language`.

Локализация — не i18n-библиотека, а простой словарь `RU_TO_EN` в
начале `App.jsx` (русская строка → английский перевод) и функция
`t(s)`, которая возвращает перевод при `language === "en"`, иначе
исходную строку без изменений. Все статические тексты интерфейса
оборачиваются в `t("...")`. Компоненты вне основного (`Header`,
`ChatThread`, `ChatInputBar`, `StarPicker`, `groupServicesByCategory`)
получают `t` явным пропом/аргументом — своего состояния языка у них
нет.

**Что не переводится (осознанное ограничение MVP):** названия
категорий/услуг, районы, введённые не из фиксированного списка,
описания мастеров, тексты отзывов — весь контент, который приходит из
базы и мог быть добавлен админом или пользователем. Переведены только
константы из фиксированных списков (`DISTRICTS`, `URGENCY_OPTIONS`,
статусы заявок) — они узнаются по значению через тот же `RU_TO_EN`.
Даты/суммы форматируются через `locale` (`ru-RU`/`en-GB`), валюта (₾)
не переводится.

Добавляя новый текст в UI — сразу оборачивать в `t()` и добавлять пару
в `RU_TO_EN`, не оставлять захардкоженную русскую строку.

## Деплой

- Домен: `goservices.lol` (backend — отдельно, `api.goservices.lol`).
- В Coolify: Build Pack автоопределяется как Node/Vite (Nixpacks),
  порт — тот, что слушает `vite preview` (см. `vite.config.js`, сейчас
  `4173`).
- `index.html` подключает `https://telegram.org/js/telegram-web-app.js`
  — обязательно для доступа к Telegram WebApp API, не убирать.
- После пуша в `main` — деплой в Coolify запускается вручную кнопкой
  Deploy.

## Локальный запуск

```bash
npm install
npm run dev
```
Вне Telegram работает через фоллбэк demo-пользователя — этого
достаточно для проверки UI, но эндпоинты, зависящие от реальных
Telegram-данных (пуш уведомлений и т.п.), проверять только внутри
самого Telegram после деплоя.

## Правила при работе над этим репо

- Не разбивать `App.jsx` на десятки файлов «для чистоты» без явного
  запроса — текущий размер проекта этого не требует.
- Дизайн — минималистичный, один акцентный цвет (`--accent`, тёмно-
  зелёный), шрифты Inter + Space Grotesk для заголовков. Не добавлять
  новые цвета/шрифты без необходимости.
- Приложение двуязычное (ru/en) — см. раздел «Локализация» выше;
  новые статические тексты оборачивать в `t()` и добавлять в
  `RU_TO_EN`, а не хардкодить по-русски.
- Мобильный экран — единственный целевой формат (Telegram Mini App
  открывается на телефоне), не оптимизировать под десктоп.
